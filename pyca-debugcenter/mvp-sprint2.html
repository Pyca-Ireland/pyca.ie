System Overview

MVP-Sprint2 is a multi-turn conversational AI interface over a vector-indexed database of LCCS (Leaving Certificate Computer Science) past exam questions. Students ask free-text questions; the system retrieves semantically similar exam questions from Pinecone, injects them as context into an OpenAI chat prompt, and streams the response back token-by-token. Retrieved questions surface as clickable cards in a sidebar and as bold inline links within the AI response text.

User types: "Show me a recursion question from HL" │ ▼ [Frontend: page.tsx] POST /api/chat → { messages, top_k: 5, filters: { level: "HL" } } │ ▼ [Next.js Route Handler: app/api/chat/route.ts] Transparent SSE pipe → FastAPI :8000 │ ▼ [FastAPI: main.py → stream_chat()] 1. Embed last user message (OpenAI text-embedding-3-small) 2. Query Pinecone (top-5, filter: level=HL) 3. Yield sources event → frontend renders sidebar cards 4. Build context block → injected into last user turn 5. OpenAI gpt-4o-mini stream → yield token events 6. Yield done event → frontend detects cited IDs, opens sidebar │ ▼ [Frontend] AI response renders as markdown [2023-AB-HL-Q5] → bold clickable button → opens QuestionModal

science_v3/search.py — SearchResult + search_questions()

SearchResult is a flat dataclass mirroring the Pinecone metadata fields plus score. It was extended in sprint2 to include pyca_goid.

@dataclass
class SearchResult:
    score: float
    exam_rid: str
    pyca_goid: str        # Added in sprint2
    year: int
    paper: str
    level: str
    number: int
    type: str
    marks: int
    page_count: int
    topics: list
    ocr_text: str         # Full OCR text — used for RAG context block
    imagery_pointer: str
    marking_pointer: str
    status: str
    qa_status: str

search_questions() flow:

  1. Embeds the query string using text-embedding-3-small (same model used at ingest time — dimension parity is critical for cosine similarity to work).
  2. Builds a Pinecone metadata filter dict from any provided year/level/paper/type arguments. Empty dict = no filter.
  3. Calls index.query(vector, top_k, include_metadata=True, filter).
  4. Maps each match to a SearchResult, safely casting types (metadata values come back as mixed types from Pinecone).
Metadata filters are applied as Pinecone pre-filters (before vector similarity scoring). This means top_k is drawn from only the matching subset — if very few documents match a filter, results may be sparse or empty.

science_v3/agent.py — stream_chat() generator

stream_chat() is a Python generator that yields dicts in SSE order. It is the central orchestration function.

def stream_chat(
    messages: list[dict],       # Full conversation history [{role, content}, ...]
    top_k: int = 5,
    filters: dict | None = None,
    openai_api_key: str | None = None,
    pinecone_api_key: str | None = None,
    chat_model: str = "gpt-4o-mini",
) -> Generator[dict, None, None]:

Execution order:

  1. Extract the last user message from the history — this is the RAG query.
  2. Call search_questions() with the query and filters.
  3. Yield {"type": "sources", "data": [...]} — serialised SearchResults, with ocr_text truncated to 300 chars for the preview field.
  4. Build the context block: one section per result, formatted as [EXAM_RID] YEAR | PAPER | LEVEL | Qn | TYPE | Nm\n{ocr_text}.
  5. Assemble the OpenAI message list: [system] + history. Context block is injected only into the last user turn — earlier turns pass through unchanged.
  6. Call client.chat.completions.create(model, messages, stream=True).
  7. For each chunk: yield {"type": "token", "data": delta}.
  8. Yield {"type": "done"}.

_to_dict() serialisation: Converts SearchResult to a plain dict for JSON. Truncates ocr_text to 300 chars as ocr_text_preview — the full text is only sent to the LLM, not to the browser.

SSE Client Loop (page.tsx handleSend)

async function handleSend(text: string) {
  // 1. Push user + empty assistant placeholder immediately
  const aId = uid();
  setMessages(prev => [...prev, userMsg, { id: aId, role: "assistant",
    content: "", sources: [], streaming: true }]);

  // 2. POST full conversation history
  const res = await fetch("/api/chat", { method: "POST", body: ... });
  const reader = res.body.getReader();
  let buf = "";

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buf += decoder.decode(value, { stream: true });
    const lines = buf.split("\n");
    buf = lines.pop() ?? "";   // Keep incomplete line in buffer

    for (const line of lines) {
      if (!line.startsWith("data: ")) continue;
      const event = JSON.parse(line.slice(6));

      if (event.type === "sources") {
        // Attach sources to the placeholder message
        setMessages(prev => prev.map(m => m.id === aId
          ? { ...m, sources: event.data } : m));
      } else if (event.type === "token") {
        // Append token to content (functional update avoids stale closure)
        setMessages(prev => prev.map(m => m.id === aId
          ? { ...m, content: m.content + event.data } : m));
      } else if (event.type === "done") {
        setMessages(prev => prev.map(m => m.id === aId
          ? { ...m, streaming: false } : m));
        // Auto-sidebar: only cited sources
        const cited = referencedSources(finalContent, pendingSources);
        if (cited.length > 0) { setSidebarSources(cited); setSidebarOpen(true); }
      }
    }
  }
}
Why not EventSource? The browser's native EventSource API only supports GET requests. Since the chat endpoint requires POST (conversation history + filters in the body), SSE is consumed manually via the Fetch API and a ReadableStream reader.

Inline Clickable Question IDs (ChatMessage.tsx)

The AI writes question references as [2023-AB-HL-Q5] in its markdown. These need to be rendered as bold, clickable buttons that open the QuestionModal. ReactMarkdown cannot natively handle this — the workaround uses a two-step process:

Step 1 — preprocessContent(): Before passing markdown to ReactMarkdown, transform all [EXAM_RID] tokens into markdown links using a custom exam:// protocol:

function preprocessContent(content: string): string {
  return content.replace(
    /\[(\d{4}-[A-Z]+-[A-Z]+-Q\d+)\]/g,
    (_, rid) => `[**${rid}**](exam://${rid})`
  );
}
// [2023-AB-HL-Q5] → [**2023-AB-HL-Q5**](exam://2023-AB-HL-Q5)

Step 2 — custom a component: ReactMarkdown's a component intercepts any link whose href starts with exam:// and renders a bold white button instead:

a({ href, children }) {
  if (href?.startsWith("exam://")) {
    const rid = href.slice(7);
    return (
      <button onClick={() => openModal(rid)}
        className="font-bold text-white hover:underline cursor-pointer">
        [{rid}]
      </button>
    );
  }
  return <a href={href} target="_blank" rel="noopener noreferrer">{children}</a>;
}

openModal(rid) looks up the source object in m.sources by exam_rid and sets it as modalSource. If the AI cited an ID that is not in the sources array (e.g. hallucinated ID), the button does nothing.

Design Decisions

Streaming Fix — Route Handler over Rewrite

The first streaming implementation used a Next.js rewrites rule in next.config.ts to proxy /api/chat → http://localhost:8000/api/chat. This caused SSE to arrive all at once in the browser — the response was accumulated by the Next.js dev server before being forwarded.

The fix: replace the rewrite with a app/api/chat/route.ts Next.js Route Handler that pipes the upstream body directly:

// app/api/chat/route.ts
export const dynamic = "force-dynamic";

export async function POST(req: NextRequest) {
  const upstream = await fetch("http://localhost:8000/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: await req.text(),
  });
  return new Response(upstream.body, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      "X-Accel-Buffering": "no",
    },
  });
}

The rewrites for non-streaming endpoints (/api/question/, /images/, /api/health) remain in next.config.ts — they are fine for request/response workloads.

No Score Threshold — AI Judgement as Single Filter

A _MIN_SCORE = 0.72 cosine similarity threshold was prototyped — results below the threshold would be dropped before being passed to the LLM. This was removed at user request.

Current approach: All top_k results are always passed to the LLM. System prompt Rule 2 ("only cite a question if it is GENUINELY relevant") and Rule 3 ("if none are a genuine match, say so honestly") are the only safeguards against the AI forcing a connection to weakly relevant questions.

Known limitation. Without a threshold, the LLM always receives 5 results. For highly specific or niche queries with no matching questions, the LLM receives contextually irrelevant data. The system prompt rules reduce hallucination but do not eliminate it.

Context Injection — Last Turn Only

RAG context is injected only into the last user message, not into the system prompt and not into prior conversation turns:

for i, msg in enumerate(messages):
    if msg["role"] == "user" and i == len(messages) - 1:
        if context_block:
            content = (
                f"Relevant exam questions from the database:\n\n{context_block}"
                f"\n\nStudent query: {msg['content']}"
            )
        else:
            content = msg["content"]
    else:
        content = msg["content"]   # All other turns: unchanged

Why: Each message to the backend triggers a fresh Pinecone search using the latest user query. Re-injecting context from previous turns would pollute the history with stale retrieval results and waste context tokens. The system prompt stays clean and constant across all turns.

System Prompt — Full Text & Rules

"You are a helpful LCCS (Leaving Certificate Computer Science) exam assistant for pyca.ie.
You help students find and understand past exam questions.
You will be given a list of exam questions retrieved from a semantic search database as context.
RULES:
1. For greetings or general conversation, respond naturally and warmly.
   You do not need to mention the database for casual messages.
2. Only cite a question by its ID (e.g. 2023-AB-HL-Q7) if it is GENUINELY relevant
   to the student's query. Do not stretch or invent a connection — if a retrieved
   question covers a different topic, do not cite it.
3. If the student asks about a specific topic or question and none of the retrieved
   questions are a genuine match, say honestly that no relevant questions for that
   topic are currently in the database.
4. Never quote or reproduce raw OCR text verbatim. Paraphrase in your own words.
5. The question image card appears automatically when you cite an ID — do not
   describe the question text in full.
6. Stay on topic: LCCS exam content and the computer science curriculum only.
7. Do not speculate about marking scheme answers."
RuleMotivation
1 — GreetingsWithout this, saying "Hi" triggered "no matching questions found" messages because the context block was empty and the AI interpreted that as a failed search.
2 — Genuine relevancePinecone returns top-5 regardless of relevance. Without this rule, the AI would cite an electric car charging question as "related to recursion" because both involve computer science.
3 — Honest no-resultsPrevents the AI from inventing an answer when no relevant questions exist. Recursion is not in the OL papers — the AI should say so, not cite an unrelated question.
4 — No OCR quotingOCR text is noisy (scan artefacts, formatting symbols). Reproducing it verbatim looks unprofessional and confuses students.
5 — Card auto-displayThe question card opens automatically on ID citation. Without this rule, the AI would describe the question in full text, duplicating the information already visible in the card.
6 — Topic scopeGuards against students using the tool as a general-purpose chatbot (weather, homework help, etc.).
7 — No marking scheme speculationMarking schemes are being assembled. Guessing answers could mislead students preparing for exams.
